# Design

## Context

kvm-gui already moves VMs between its own hosts as bundles (`internal/core/bundle.go`, `bundle2.go`): an uncompressed tar read as untrusted input, exported under `recoverSnapshotOps` + reload + `lockRun` so no start or snapshot operation changes the disks while they are read, and imported through `createImported` with a fresh identity. Clones convert disks with `qemuImg`. Linux, Windows and Other VMs (`guest.go`) have a profile, firmware (`bios`/`uefi`), Secure Boot, TPM (swtpm state in the VM folder), disks with a format (`qcow2`/`raw`) and a bus (`virtio`, `sata`, `nvme`), optical drives, NICs (`nat`, or `bridged` to one of the host's bridges, `network.go`; models `virtio-net-pci`, `e1000e`, `e1000`), graphics and a resolution.

On the reference host, VirtualBox 7.2.10 is installed. A VirtualBox-made OVF (a Vagrant box) shows what VirtualBox writes: OVF 1.0, `References` → `File`, a `DiskSection` with `vmdk.html#streamOptimized` disks and `ovf:capacity` with `ovf:capacityAllocationUnits` (GiB there), `NetworkSection`, one `VirtualSystem` with `OperatingSystemSection` (`ovf:id` 101 for `Linux_64`, plus `vbox:OSType`), `VirtualHardwareSection` rasd items (ResourceType 3 CPU, 4 memory, 5 IDE, 20 other storage with `rasd:ResourceSubType` AHCI, 17 disk, 10 Ethernet, 35 sound) and a `vbox:Machine` extension; VirtualBox 7.2's own `.vbox` files record EFI as `<Firmware type="EFI"/>`. VirtualBox's exporter writes the manifest after the payload, and VirtualBox's OVF reader does not use VMware's `vmw:Config firmware` key (Codex review of this change, from Oracle's reader).

## Goals / Non-Goals

**Goals:**
- Import common Linux and Windows appliances from VirtualBox 7, VMware and other OVF tools without manual fixes, and say plainly what was dropped.
- Write appliances that VirtualBox 7.2 imports and boots with the right OS type, firmware, disks and NICs, proven by a real import in an isolated VirtualBox configuration.
- No new Go module: `encoding/xml`, `archive/tar`, `crypto/sha1`, `crypto/sha256`, `qemu-img`.

**Non-Goals:**
- macOS appliances (OpenCore, Reims vGPU and Apple's licensing do not map to OVF); kvm-gui bundles stay the way to move them, as well as snapshots and TPM state.
- Importing snapshots, saved state, NVRAM, TPM state, USB filters, shared folders, multiple monitors, floppy drives, serial ports; audio beyond on/off.
- Compressed (`ovf:compression`), chunked (`ovf:chunkSize`) files, OVF environment and properties, `VirtualSystemCollection`, ARM appliances: refused with the reason.
- The GUI dialogs for kvm-gui bundles (migration change `migrate-gui-to-go-wails`, task 7.7): separate menu items, separate operations.

## Decisions

**D1. A neutral appliance model.** The reader parses the descriptor into a small struct (name, description, OS: CIM id, VirtualBox OS type and architecture; CPUs, memory in bytes, firmware, Secure Boot; controllers with type and subtype; disks with file, format URI, declared capacity in bytes and controller slot; optical drives; NICs with attachment, adapter type and host interface name), then a mapper turns it into a complete `Config` plus "not kept" notes, and the planned `Config` goes through the same validation as a save. The writer goes from a `Config` to the same struct and then to XML. Mapping stays testable without XML, and `vbox:Machine` and the standard sections feed one struct.

**D2. OVF 1.0 and 2.0 parsing.** Elements are matched by namespace URI, not prefix: the envelope (`http://schemas.dmtf.org/ovf/envelope/1` or `/2`), rasd, vssd, sasd and epasd (`http://schemas.dmtf.org/wbem/wscim/1/cim-schema/2/CIM_*SettingData`), VirtualBox's (`http://www.virtualbox.org/ovf/machine`) and VMware's. Hardware comes from `Item` (rasd), and in OVF 2 also `StorageItem` (sasd) and `EthernetPortItem` (epasd). Controller type comes from ResourceType plus `ResourceSubType` (`PIIX3`/`PIIX4` IDE, `AHCI` SATA, `LsiLogic`/`BusLogic` SCSI, `NVMe`, `VirtioSCSI`), not from ResourceType alone. Capacities apply `capacityAllocationUnits` (`byte * 2^n` forms) with overflow checks. An unknown section or item with `ovf:required` true (the OVF default for items) refuses the import; unknown optional ones become notes.

**D3. Which source wins on import.** `vbox:Machine` when present (firmware `Firmware type="EFI"` in `Hardware` or `Platform`, Secure Boot, OS type, adapter types and attachments), else the standard sections, else the chosen profile's defaults. Firmware without `vbox:Machine`: VMware's `vmw:Config` key `firmware=efi`, else BIOS, with a note that the firmware was assumed.

**D4. Firmware and OS on export, settled before the writer.** Task 3.0 builds candidate descriptors for BIOS and EFI Linux and Windows 11 VMs (with Secure Boot) and imports them for real into VirtualBox 7.2.10 in an isolated VirtualBox: a throwaway `VBOX_USER_HOME`, a unique `VBOX_IPC_SOCKETID` (so the clients start their own VBoxSVC instead of reaching the user's, whose IPC endpoint does not depend on `VBOX_USER_HOME`) and a machine folder inside the throwaway home; before any import it checks that `VBoxManage list vms` there is empty and that the user's `VirtualBox.xml` is unchanged afterwards. It then reads the result with `VBoxManage showvminfo --machinereadable`. The candidate kept is the smallest `vbox:Machine` that VirtualBox accepts and that yields EFI, Secure Boot, OS type, CPUs, memory, controller, disk and NIC as intended, alongside complete standard sections; it is recorded here with the dry-run and showvminfo output, and the writer (3.1) implements exactly that. If no reduced `vbox:Machine` is accepted, the export writes standard sections only and the EFI requirement is reported as a known limitation before shipping, with the spec amended.

**Task 3.0 result (2026-11-08, VirtualBox 7.2.10r174163, isolated as above; the user's `VirtualBox.xml` checksum unchanged, the isolated VBoxSVC gone afterwards).**
- *Disks:* a streamOptimized VMDK written by `qemu-img` (8.2.2 and 10.2.1 alike) imports only when every grain holds data: a disk half data, half zeros failed at 40% with `VBOX_E_FILE_ERROR` / `VERR_EOF`, which real disks always are. A monolithicSparse VMDK written by `qemu-img convert -O vmdk -o subformat=monolithicSparse` imports, declared `vmdk.html#sparse` (or `#streamOptimized`), and `qemu-img compare` found the imported disk identical. A first conclusion, monolithicSparse disks, held only for small disks: inside an `.ova` VirtualBox reads the disk as a stream, and a 1 GiB monolithicSparse disk aborted (`NS_ERROR_ABORT`) while the same appliance unpacked as an `.ovf` imported. VirtualBox's own streamOptimized export shows the stream layout the format defines (each grain table after its grains, only non-empty tables, the grain directory, a footer and an end-of-stream marker; flags `0x30001`, overhead 128 sectors), which qemu-img's output lacks (its tables are at the start, flags `0x30003`, no markers). So the export writes streamOptimized disks with kvm-gui's own writer (`internal/core/vmdk.go`, from a sparse raw image made by qemu-img), declared `#streamOptimized`.
- *Firmware:* VMware's `vmw:Config firmware=efi` is ignored (the VM came out BIOS). A `vbox:Machine` needs at least `Memory RAMSize` ("Required Memory/@RAMSize element/attribute is missing"), and once present VirtualBox builds the machine from it alone (a CPU count it lacks became 1) and refuses a disk the `vbox:Machine` does not attach ("contains a medium attachment for the disk image but the OVF describes no such image"). The kept form, accepted for Ubuntu and Windows 11: `<vbox:Machine ovf:required="false" version="1.16-linux" uuid=… name=… OSType=…>` with `Hardware` holding `CPU count`, `Memory RAMSize`, `Firmware type="EFI"` (omitted for BIOS), `TrustedPlatformModule type="v2_0"` when the VM has a TPM, `Network/Adapter slot enabled type` with `<NAT/>` or `<BridgedInterface name=…/>`, and one `StorageControllers/StorageController name="SATA" type="AHCI" PortCount=… Bootable="true"` attaching each disk (`AttachedDevice type="HardDisk" port device` with `Image uuid` equal to the disk's `vbox:uuid` in the `DiskSection`) and each optical drive (`type="DVD"`, empty). Result: OS type, firmware EFI, CPUs, memory, SATA disk, empty DVD, NAT and the TPM as intended. Secure Boot has no place in it (VirtualBox 7 keeps it in the NVRAM file): the export notes it.
- *OS ids without `vbox:OSType` (dry runs):* 94 → `Ubuntu_64`, 96 → `Debian_64`, 80 → `RedHat_64`, 101 → `Linux26_64`, 120 → `Windows10_64`, 102 → `Other_64`, and 122 → `Other`; VirtualBox's own export of a `Windows11_64` VM writes CIM id 120 with `vbox:OSType` `Windows11_64`, so Windows 11 exports as 120 too.
- *Manifest and adapters:* a `SHA256(name)= hex` manifest in an OVF 1.0 appliance is accepted (VirtualBox's own export writes none by default; its order is descriptor, then disks). Adapter types written: `virtio` for virtio-net-pci, `82540EM` for e1000 and e1000e.

**D5. OS table with CIM ids.** One table maps kvm-gui profiles to VirtualBox OS types and DMTF CIM `OperatingSystemSection` ids and back: `ubuntu` ↔ `Ubuntu_64` / 94, `debian` ↔ `Debian_64` / 96, `rocky` ↔ `RedHat_64` / 80, `fedora` ↔ `Fedora_64` / 101, `arch` ↔ `ArchLinux_64` / 101, `opensuse` ↔ `OpenSUSE_64` / 101, `linux` ↔ `Linux_64` / 101, `windows10` ↔ `Windows10_64` / 120, `windows11` ↔ `Windows11_64` / 120 (as VirtualBox writes it; 122 is read as Windows 11 too), `other` ↔ `Other_64` / 102 (DMTF CIM_OperatingSystem.OSType values); the Windows CIM ids and every id above are confirmed in task 3.0 by importing descriptors without `vbox:OSType` and checking the OS type VirtualBox picks. Import accepts VirtualBox's variants by bounded alias lists (`Ubuntu*_64`, `Debian*_64`, `RedHat*_64`, `Oracle*_64` → `rocky`, `Windows10*_64`/`Windows2016_64`/`Windows2019_64` → `windows10`, `Windows11*_64`/`Windows2022_64`/`Windows2025_64` → `windows11`); an unlisted type falls back to the CIM id's family (Linux, Windows), else Other, with a note. Architecture suffixes other than x86 (`_arm64`) refuse the import; 32-bit types import as the same family.

**D6. Two-pass import with staging.** Pass 1 reads the archive's headers only (seeking past file data; an `.ovf` lists its folder's referenced files): flat names, plain files, no duplicates, at most 64 members, descriptor first and at most 4 MiB, then parses the descriptor and checks every referenced file exists and no other file is there besides a manifest or certificate; it also sums the members' sizes and checks that the destination folder's file system (the parent of the chosen folder, which may be outside the workspace) has that much free plus 1 GiB. Nothing is written before pass 1 succeeds. Pass 2 creates the VM folder as a temporary sibling of the destination (`.import-*` in the same parent, so the final rename never crosses file systems), extracts each referenced file into it while hashing (SHA-1 and SHA-256), then checks the manifest when present: `SHA1(name)= hex` or `SHA256(name)= hex` lines, one per file, covering the descriptor and every disk, no duplicate names, every digest matching; an appliance whose descriptor is not covered by its manifest is refused.

**D7. Disk images are inspected before conversion.** First kvm-gui reads each extracted disk's header itself, before qemu-img opens it, since qemu-img opens a VMDK's extents and a qcow2's backing file while reading metadata: a declared VMDK must start with the hosted sparse magic `KDMV` (a text descriptor, which is how multi-file and flat VMDKs look, is refused) and its embedded descriptor must say `createType` `monolithicSparse` or `streamOptimized` with exactly one extent; a declared qcow2 must have no backing-file offset and no external-data-file feature bit; a declared raw image is not interpreted. Then, with `-f <declared format>` on every qemu-img call (never probing), `qemu-img info --output=json` on the staged file (format from the `DiskSection` URI: `vmdk` for the VMware URIs, `qcow2`, `raw`), refusing any `backing-filename`, a qcow2 `data-file`, a VMDK whose `create-type` is not `monolithicSparse` or `streamOptimized` (single-file), any VMDK extent other than the staged file itself, a virtual size different from the declared capacity (rounded to its unit) or over 16 TiB. Then `qemu-img measure -O qcow2` gives the space the conversion needs; it is checked against free space, and `qemu-img convert -f <format> -O qcow2 -o compat=1.1` writes the disk into the staging folder. qemu-img only ever sees staged file names (no protocols, no `json:` names), and runs as the user with the context for cancellation, under `prlimit` (2 GiB address space; `info` and `measure` also a 120 s time limit) so a hostile image cannot exhaust the host. The converted image is checked once more for a backing file. Disk bus: the imported controller when kvm-gui has it (SATA → `sata`, NVMe → `nvme`); kvm-gui has no virtio-scsi or IDE/SCSI controllers, so VirtioSCSI → `virtio` (virtio-blk) and IDE/SCSI → `sata`, each with a note that the guest needs that driver at boot; an appliance without controller information uses the profile's bus.

**D8. Identity, then publish.** The planned `Config` gets new MACs, an SSH port (`NextSSHPort`), a fresh OVMF VARS file for UEFI (VirtualBox's NVRAM is not imported: guests boot through their fallback loader `EFI/BOOT/BOOTX64.EFI`, noted), no TPM state (a Windows 11 TPM starts empty, noted with the BitLocker recovery key). The staging folder is renamed to the VM folder (`os.Rename` of a directory fails if the target exists and is not empty, and the name is chosen free), and the DB row is written last through `createImported`; the import owns the final folder until that row exists, so a failure at any step, the registration included, removes the staging or the final folder (as `CloneVM` does).

**D9. Export.** Under `recoverSnapshotOps`, reload and `lockRun` for the whole export (as `ExportBundle`), refusing a running VM and a disk another running VM has open. Each disk is converted by `qemu-img convert -f <its format> -O raw` to a sparse raw image in a staging folder beside the destination, then written as a streamOptimized VMDK by kvm-gui's writer (task 3.0: VirtualBox needs the stream layout, which qemu-img does not write), then hashed; the descriptor is generated with the converted sizes; the tar is written as descriptor, disks, manifest (`SHA256(name)= hex`, accepted by VirtualBox 7.2 for OVF 1.0) into a temporary file beside the destination; publication is `link(2)` of the temporary file to the destination name (fails if it exists) and unlink of the temporary, or `rename(2)` when overwrite was allowed. The destination is refused if it resolves (same device and inode, or same path) to any file the VM uses: its disks wherever they are, its ISOs and its folder's files. Secure Boot goes in the descriptor in the form task 3.0 records; if VirtualBox has none, the export notes that Secure Boot must be turned on again there. Disk bus mapping: `sata` → SATA (AHCI), `nvme` → NVMe, `virtio` → SATA with a note that the guest needs the AHCI driver in its initramfs (standard in the distributions kvm-gui profiles); the exported controller is reported in the summary.

**D10. Surfaces.** Core `PlanImport(src, opts)` (the dry run: planned VM, notes, needed space), `ImportAppliance(ctx, src, opts, progress)` and `ExportAppliance(ctx, entry, dst, opts, progress)`; the CLI and MCP call them like the bundle commands; the GUI adds File › Import Appliance… (picker, preview from `PlanImport` with name, folder and bridge choices, progress with Cancel) and File › Export Appliance… (save picker, snapshots/TPM notes with the acknowledgment, overwrite confirmation, progress with Cancel), apart from the bundle items of task 7.7.

## Risks / Trade-offs

- [VirtualBox rejects every reduced `vbox:Machine`] → standard sections only, EFI documented as a manual step, decided in task 3.0 before any writer code (D4).
- [Guests whose initramfs lacks the target disk driver] → controllers kept where kvm-gui has them; virtio→SATA on export and IDE/SCSI→SATA on import are noted; boot tests in tasks 2.3 and 4.4 cover both directions.
- [UEFI guests without a fallback loader] → noted at import; Windows repairs its boot files from its install media.
- [qemu-img parsing a hostile image] → D7's inspection before any conversion, declared format only, staged names only; qemu-img still parses the file, as every importer must.
- [Peak space] → pass 1 checks the extraction space, D7 measures each conversion before it runs; the temporary extracted image is removed after its conversion, so the peak is one image plus its conversion.

## Migration Plan

Additive: no stored data changes. Rollback is removing the commands, tools and menu items.
