# Design

## Context

See `proposal.md` › Why. Current state that shapes the approach:

- `internal/core` (one GUI-free package) already owns everything a VM needs: configuration and validation, SQLite store (schema 5), Workspace locks, QEMU arguments and process, QMP, a minimal RFB client (`vnc.go`), running-VM discovery through `/proc`, installers, GPU, Reims vGPU. `cmd/` (Cobra) and `internal/mcp` sit on top of it. The codebase graph shows `internal/gui` → `internal/core` (218 calls) and `internal/gui` → `internal/embed` (53) as the GUI's only dependencies, so the GUI can be replaced without touching the core's contract.
- The Fyne GUI (`internal/gui`, ~4.5k lines) is one VirtualBox-like window with tabs (Details, Screen, Install, Host, GPU, Log), and runs one VM, owned by the GUI process (`Pdeathsig`).
- `internal/embed` embeds Reims vGPU's SDL3/Vulkan window via cgo over Rust's `rg-x11-ffi`, a static library pruned to keep the binary's glibc floor at 2.38.
- The MCP server already starts VMs as detached `vm start` processes and attaches through the run's VNC socket and a second QMP socket (`qmp-control.sock`).
- goXterm (`/home/nilton/Projetos/nilton/NOVOS/goXterm`) is the house pattern: Go at the root, Wails v3.1, Vue 3 + Vite Plus (`vp`) + Tailwind 4 in `frontend/`, built into `internal/gui/dist` and embedded; Docker image `build/linux.Dockerfile` (Ubuntu 24.04, GTK 4 + WebKitGTK 6.0, appimagetool); `make check test layers build appimage`; `internal/archtest` enforces that only `internal/gui` imports Wails; release assets are `-linux-amd64` + `-x86_64.AppImage` + `SHA256SUMS`.

## Goals / Non-Goals

**Goals:**
- One Go app on goXterm's layout and toolchain, with no Rust and no cgo except what GTK/WebKit linking needs.
- VirtualBox workflow parity, tracked row by row in a parity matrix (`docs/parity-virtualbox.md`).
- Ordinary KVM guests on the same core, CLI and MCP as macOS VMs.
- Existing users keep every VM and setting with no manual step.

**Non-Goals:**
- libvirt, remote hosts, migration, cloud VMs, OVF/OVA appliances, unattended install, Guest Additions, shared clipboard and drag and drop, seamless mode, multiple monitors, live snapshots, linked clones, VM groups, UI translations.
- Windows or macOS hosts; any architecture other than amd64.
- Pixel identity with VirtualBox: the look is our own (goXterm-style themes).

## Decisions

### D1: Wails v3 + Vue 3 + Vite Plus + Tailwind, laid out like goXterm
User decision. `frontend/` (Vue 3 SFCs, Tailwind 4, `vp build` into `internal/gui/dist`, embedded with `//go:embed`); `internal/gui` holds the Wails application, its bound services and the loopback stream server; it is the only package importing Wails, checked by an `internal/archtest` test ported from goXterm. One binary, one Cobra command tree (as today's `cmd/`): `kvm-gui` / `kvm-gui gui` opens the GUI (`--self-test`, `--safe-gpu` as Cobra flags), every CLI command is a subcommand with Cobra flags, `kvm-gui mcp` serves MCP, and internal options (`vm start --gui-run --embed-x11`) are hidden flags. Pinned versions are those goXterm ships (Wails 3.1.0, `@wailsio/runtime` 3.1.0, Vue 3.5, Tailwind 4.3, Vite Plus 1.5.0), installed only inside Docker.
- Alternatives: keep Fyne (hand-drawn widgets, the reason for this change); Svelte/React (diverges from the house pattern for no gain).

### D2: References used for behavior, never copied
VirtualBox (`VirtualBox/virtualbox`, GPLv3: Manager, `wizards/newvm`, `settings/machine/*`, `runtime/` menus and `UIVMCloseDialog`), virt-manager (GPLv2+: `createvm`, `details`, `addhardware`, `snapshots`, `clone`, and its libosinfo-driven device defaults) and webvirtmgr (Apache-2.0: instance list, console page) are the functional reference: which screens exist, which options each offers, which device defaults each OS gets. The project is BSD-3-Clause, so no code, UI files, strings, icons or artwork from the GPL projects are copied; webvirtmgr code is not reused either (Python/Django on libvirt, nothing transfers). The parity matrix cites the reference screen for each row. Icons stay original SVGs (`internal/assets/icons`), extended for guest types. For everything Reims vGPU, `steelbrain/reims-vgpu` (its README, `docs/qemu.md`, `docs/architecture.md` and `reims-ctl`) is the base: the docs link to it as the source of truth for the GPU, its QEMU, `reims-ctl`, guest setup (`METAL_ERROR_MODE`) and host requirements, and repeat only what kvm-gui adds.

### D3: No libvirt; the app keeps owning QEMU
The core already builds QEMU's command line, which Reims vGPU's forked QEMU, OpenCore on `vvfat`, the per-run private sockets and the MCP attach model all depend on. libvirt would need a domain XML for each of those, a daemon and group membership the project deliberately avoids ("Groups not needed"). Ordinary guests reuse the same path: `BuildArgs` branches on guest type. New macOS VMs on Reims vGPU are the one exception: upstream's `reims-ctl` creates and launches them (D19), and the app still adds its own VNC and QMP sockets.

### D4: VMs run as detached processes, with one QMP socket per client
The GUI starts a VM the way the MCP server does: a detached `kvm-gui vm start` child (its own session, output to the run log), then attaches through the run's VNC socket. QEMU gets one more QMP monitor, `qmp-gui.sock`, next to the owner's `qmp.sock` and the existing `qmp-control.sock` (MCP and CLI), so the GUI and an agent never compete for one socket; each client reconnects on its own after a drop and gets events on its own monitor. This gives several VMs at once and VMs that outlive the Manager (VirtualBox's model). The foreground `vm start` in a terminal is unchanged.
- **Run records.** Every owner (GUI, CLI, MCP) writes `run.json` in its private run directory (0700, `$XDG_RUNTIME_DIR/kvm-gui/<vm id>/`): VM id, QEMU pid, its start time from `/proc/<pid>/stat` field 22, a run generation id and the starter (`gui`, `cli`, `mcp`). The app finds and controls its own runs only through these records, checked against `/proc` (same pid and start time); a shared disk never makes another VM's run its own. A VM without a hard disk (live ISO) is found the same way.
- **GUI runs.** The GUI passes a hidden `--gui-run` flag; the record then says `gui`. Only when the GUI has a usable X11 parent (X11 or XWayland) does it also pass `--embed-x11`, which sets the existing `EmbedX11` option (so `reimsEnv` gives QEMU `SDL_VIDEO_DRIVER=x11`); on Wayland without XWayland, Reims keeps its native Wayland window. A GUI that embeds the run holds an `flock` on `gui-run.lock`; a later GUI may embed it only when pid and start time still match and the lock is free (`screen-embedding` › Run ownership survives the GUI). CLI and MCP runs are never embedded.
- **Disks in use.** Busy detection (`running.go`) moves from "the process has `<folder>/mac_hdd_ng.img` open" to "any process has any of the VM's hard disk images open", compared by `(st_dev, st_ino)` of `/proc/<pid>/fd/*` targets against `stat()` of every disk path, so symbolic links, relative paths and shared images resolve to one identity. A busy VM without its own run record shows as running outside the app and is never controlled. Every operation locks each image it touches with an `flock` keyed by its `(dev, ino)` in `$XDG_RUNTIME_DIR`, whoever owns the image, in a fixed order (by identity) to avoid deadlocks, and rechecks busy state under the locks; the Workspace lock per VM folder stays.
- Alternative: GUI-owned children with `Pdeathsig` (today). Rejected: it forces one owner and kills VMs when the GUI crashes.

### D5: Screen = Go RFB → canvas over an authenticated loopback WebSocket
The existing RFB client decodes frames in Go; dirty rectangles are sent as binary messages to a `<canvas>` over a WebSocket on `127.0.0.1:<random port>`. Input (scancodes, absolute pointer, buttons, wheel) flows back on the same socket. Wails events carry control-plane notifications only (state, logs).
- **Origin.** Exactly the origin Wails serves the SPA from on Linux (recorded by the scaffold task and asserted by a test); a missing, `null` or other `Origin` is refused before the upgrade.
- **Token.** 256 random bits per GUI launch, returned to the page by a bound Wails service method, sent as the first message (never in the URL), compared in constant time; no first message within 2 s closes the connection. The token is never logged.
- **Binding.** The first message also names the VM and its run generation (D4); the server closes every connection of a run when it ends, so a viewer never reaches a later run. Client messages over 64 KiB close the connection. On close, every key and button the viewer pressed is released in the guest.
- **Flow control.** One frame in flight per viewer; newer updates coalesce while the previous one is drawn.
- Alternatives: noVNC (puts RFB in JavaScript and still needs a WebSocket-to-Unix proxy); Wails events for frames (base64 JSON, too slow at 1080p60).

### D6: Reims window embedding in pure Go X11
GTK 4 removed GDK's foreign-subwindow support, so the embedding works below GTK, on raw X11 with `github.com/jezek/xgb` (BSD-3-Clause, pure Go): it embeds only in an X11 session (never on Wayland, XWayland included: see the 6.4 result below). It finds its own VM window by `_NET_WM_PID` = its pid and a unique `WM_NAME` token, finds the Reims window by `_NET_WM_PID` = the run's QEMU pid, adds it to the save-set (`ChangeSaveSet`, so the X server reparents it to the root if the GUI dies), reparents it into the VM window, places it over the canvas rectangle the frontend reports (ResizeObserver × `devicePixelRatio` + the webview's offset), unmaps it while an HTML dialog or menu is open (the frontend reports overlay state) and reparents it back before the VM window closes or the GUI exits. The window-manager hand-off rules of `archive/rust/reims-gui/crates/rg-x11` (focus, `_NET_ACTIVE_WINDOW`, release order) are ported, not reinvented.
- **Spike first.** Task 2.1 proves this on GTK 4 + WebKitGTK 6.0 before the core work: parent XID discovery, a real SDL3/Vulkan window (lavapipe in the GNOME containers, Reims vGPU on the reference host), HTML overlay hiding, native menu popovers, focus hand-off, scale change and SIGKILL survival.
- **Spike result (2026-11-08): go, with one change.** In the build image (Xvfb, openbox, GTK 4.14.5, WebKitGTK 2.52.6, Wails 3.1.0, `GDK_BACKEND=x11`): the Wails window found by `_NET_WM_PID` and its `WM_NAME` token; a client found by its `_NET_WM_PID` (`xclock`) and a Vulkan client (`vkcube` on llvmpipe) reparented into the page's rectangle, drawn there, hidden (the page shows through) and resized. The save-set must be held by the X connection that created the parent window, which is GTK's, not xgb's: with xgb's own connection a SIGKILL destroyed the guest window and its client exited; with `XAddToSaveSet` on GTK's Display (`gdk_x11_display_get_xdisplay`, one small cgo function, called on the UI thread) the client survived and its window went back to the desktop. So embedding is xgb plus that one call; the binary already links GTK through cgo, so no dependency is added. Clients that set no `_NET_WM_PID` (vkcube) are out of scope: Reims vGPU's SDL3 window sets it. Still to check in 6.4/6.6: KWin and Mutter (the reference host runs KDE Plasma on X11), HiDPI, focus hand-off, and Reims vGPU's own window on the RTX 4070.
- **No-go.** If the spike fails, implementation stops and this change is amended first: `screen-embedding` is removed, `reims-vgpu` › Display returns to "Reims vGPU's own window", tasks 6.4 and 6.6 drop embedding, and the gate in 9.1 drops its embedding items. Nothing ships with an untested half of it.
- **6.4 result (2026-11-08).** Three findings from the reference host (KDE Plasma on X11) and `scripts/check-gnome.sh` (clean Ubuntu containers): (1) under a reparenting window manager the move itself sends a ReparentNotify to the root; reading it as "window lost" got the container destroyed with QEMU's window inside (QEMU died of a BadWindow on KDE), so `Embed` reads the X tree after the move and `Release` never destroys a container that still holds the window. (2) On SIGKILL a plain save-set moves the window to the closest ancestor the GUI did not create, which under mutter (`mutter-x11-frames`) or KWin is the frame of the GUI's window, and the window manager then destroys that frame with the VM's window in it. Both owning connections (GTK's, through `XFixesChangeSaveSet` with its X error trapped, and the container's, through xgb) use XFixes' save-set with the root target and mapping, so the X server itself puts the window on the root, mapped; embedding is refused when that fails. (An intermediate design with a guard process racing the frame's teardown was dropped for it.) `TestSIGKILLUnderWindowManager` fails with a plain save-set against a fake window manager that destroys the frame at once, and passes with the root target. (3) On Ubuntu 26.04 GNOME is Wayland only (mutter 50 has no X11 backend), and XWayland 24 segfaults when a client that holds another client's window dies, with or without the guard, taking mutter and every X11 client with it; so the GUI never embeds on a Wayland desktop (no `GDK_BACKEND=x11`), and the guest stays in Reims vGPU's own window there.
- Consequences: no Rust, one cgo function for the save-set only (`XFixesChangeSaveSet` on GTK's Display), no `reims_embed` tag, no `ld -r --gc-sections` pruning; `make test-embed` becomes a pure-Go test under Xvfb.

### D7: Guest types, OS profiles and the data model
The database stays one SQLite file through the pure-Go `modernc.org/sqlite` driver the core already uses (v1.60.1, WAL, `PRAGMA user_version`): no cgo, no SQLite package on the host, no server. As built, schema 6 keeps the new per-VM fields in one JSON column `ext` (one idempotent migration step instead of one per field); they are, as planned: `guest` (`macos` default, `linux`, `windows`, `other`), `profile`, `firmware` (`uefi`/`bios`), `secure_boot`, `tpm`, `disks` (JSON: path, format, bus, owned), `optical` (JSON), `boot_order`, `audio`, `usb` (controller and passthrough devices), `serial`, `shared_folders`, `description`, `current_snapshot`, `backend` (`app` default, `reims-ctl`), `reims_ctl_name`; and a table `snapshots(id, vm_id, parent_id, name, description, created_at, manifest)`, where `manifest` is JSON: each disk's path, format and qcow2 snapshot tag, the copied VARS and TPM files, and the VM settings at that time. Each step is idempotent and the version is written last, as today. The upgrade never migrates the old file: D20 copies it with `VACUUM INTO` to the new data folder and migrates the copy, so `~/.config/macos-kvm-gui/macos-kvm-gui.db` stays at schema 5 and an older `macos-kvm-gui` keeps working on it (without seeing later changes). Later schema bumps write `kvm-gui.db.schema<N>.bak` next to the database first. The new binary refuses a schema newer than it knows.
macOS VMs keep `mac_hdd_ng.img` and `BaseSystem.img` as fixed names; their new fields stay empty. OS profiles are a small Go table modeled on virt-manager/libosinfo defaults:

| Profile | Firmware | Disk | NIC | Graphics | Extras |
| --- | --- | --- | --- | --- | --- |
| Linux (Ubuntu, Debian, Fedora, Rocky/RHEL, Arch, openSUSE, generic) | UEFI | virtio-blk | virtio-net-pci | virtio-vga | ich9-hda, usb-tablet, virtio-rng |
| Windows 10 | UEFI | SATA | e1000e | VGA (std) | hv_* enlightenments, ich9-hda, usb-tablet |
| Windows 11 | UEFI + Secure Boot | SATA | e1000e | VGA (std) | TPM 2.0 CRB, hv_*, ich9-hda, usb-tablet |
| Other | BIOS | SATA | e1000 | VGA (std) | usb-tablet |

Windows defaults to emulated disk and NIC so setup needs no driver disc; the user can switch to virtio and attach a virtio-win ISO as a second optical drive. The network models per guest type are in the `networking` delta; `networks: null` versus `[]` keeps its current meaning for macOS VMs, and ordinary guests are always created with an explicit list.

### D8: Firmware, Secure Boot and TPM from the host
- **Firmware pairs.** A path table per distribution lists matching CODE/VARS pairs: Ubuntu/Debian `ovmf`: `OVMF_CODE_4M.fd` + `OVMF_VARS_4M.fd`, `OVMF_CODE_4M.secboot.fd` + `OVMF_VARS_4M.ms.fd`; Rocky 10 `edk2-ovmf`: `OVMF_CODE.fd` + `OVMF_VARS.fd`, `OVMF_CODE.secboot.fd` + `OVMF_VARS.secboot.fd`. Only a pair from the same row is used. The VARS template is copied once into the VM folder; toggling Secure Boot replaces it from the other pair after confirmation. Secure Boot adds `-machine q35,smm=on` and `-global driver=cfi.pflash01,property=secure,value=on`; BIOS with Secure Boot is invalid. macOS keeps the embedded Debian OVMF it uses today.
- **Proof.** The host check confirms the files; the integration tasks confirm enforcement in the guest (`mokutil --sb-state`, an unsigned EFI program refused; `Confirm-SecureBootUEFI` on Windows).
- **TPM.** The owner starts `swtpm socket --tpm2 --tpmstate dir=<vm>/tpm,mode=0600 --ctrl type=unixio,path=<run>/swtpm.sock --terminate` with umask 077, the `tpm/` directory 0700, and waits up to 5 s for the control socket before starting QEMU, which gets `-chardev socket,id=chrtpm,path=... -tpmdev emulator,id=tpm0,chardev=chrtpm -device tpm-crb,tpmdev=tpm0`. On every exit path (QEMU start failure, crash, normal exit) the owner waits up to 10 s for `swtpm` to exit, kills and reaps it if needed, and releases the Workspace lock only after that, so snapshot, clone and move never read a half-written state. Snapshot and clone copies keep mode 0600.

### D9: ISO detection offline
Read the ISO 9660 primary volume descriptor's volume id (and the Joliet/UDF label when present) and match a pattern table (`Ubuntu*`, `debian-*`, `Fedora-*`, `Rocky-*`, `CCCOMA_X64FRE_*`/`CPBA_X64FRE_*` for Windows, …). No network, no mounting. Unknown labels leave the choice to the user.

### D10: Offline snapshots with qemu-img, as journaled transactions
- **Eligibility:** every hard disk qcow2, none referenced by another VM or another VM's snapshot manifest; ISO files and `BaseSystem.img` are install media and are skipped.
- **Journal:** take, restore and delete each write `<vm>/snapshots/.op-<id>.json` (fsync'd file and directory) before the first change, listing every step with its inverse, and update it after each step. Each operation ends with one database transaction that also writes the operation id into `snapshot_ops`; recovery on open (GUI, CLI, MCP) reads the journal, rolls forward when that id is in `snapshot_ops`, otherwise rolls back, then deletes the journal.
- **Take:** `qemu-img snapshot -c <tag>` per disk, copy VARS and the TPM directory into `<vm>/snapshots/<id>/`, then insert the row. Rollback deletes the tags created and the folder.
- **Restore:** preflight (powered off, every manifest file present, free space), then a hidden `pre-restore-<op>` qcow2 snapshot of every disk in the union of the current attachments and the target manifest, and copies of the current VARS, TPM and settings; apply the snapshot step by step; commit settings, `current_snapshot` and the op id in one transaction; remove the hidden snapshots and copies. Rollback applies the pre-restore copies.
- **Delete:** mark the row `deleting` (one transaction), `qemu-img snapshot -d` its tag on each disk in its manifest (a missing tag counts as done, so retries are idempotent), remove its folder, then delete the row and re-parent its children (one transaction with the op id). A row left `deleting` is finished on open, never shown as restorable: unlike take and restore, a delete only rolls forward once `deleting` is committed, because a removed tag cannot be recreated.
- All operations hold the VM's Workspace lock and the image locks of D4. Failure-injection tests cover each step of each operation, ENOSPC, cancellation and a kill at each step followed by reopening.
- Live snapshots are a non-goal: `savevm` needs every writable block device to support snapshots, and the raw pflash VARS and OpenCore's `vvfat` disk do not.
### D11: Full clone only; the TPM is copied by default
`qemu-img convert -O qcow2` of every attached hard disk (owned or external; sources are opened read-only and never changed) into the new folder, copy VARS and the TPM state (BitLocker keeps working), new MACs (default), the next free SSH port (as `unique-ssh-ports` does) and a new SMBIOS identity for macOS. "New TPM" is an option with the BitLocker warning. A failure removes the new folder. Linked clones are a non-goal: a qcow2 backing file must never change, which would require rebasing the source VM onto a new overlay. Move, export, import and delete use the same owned-file inventory (`vm-management` › Files a VM owns): bundles gain a format version 2 with `disks/`, `tpm/` and `snapshots/` entries and the same name allowlist and traversal checks; a bundle with TPM state is created 0600, its `tpm/` entries are written 0600 in the tar, and import forces 0700/0600 whatever the archive says; version 1 bundles import unchanged. Delete and move refuse a file another VM or snapshot references.

### D12: Name and command compatibility
Binary, window title, desktop file, AppImage and packages are `kvm-gui`. When `os.Args[0]`'s base name is `macos-kvm-gui`, the binary behaves the same (the packages ship that link, so MCP registrations keep working). Files move to the XDG layout (D20); `MKG_*` variables stay accepted next to `KVM_GUI_*`. Host files under `/etc` (`modprobe.d`, `sysctl.d`, `udev`) keep their current `macos-kvm-gui` names: they are system configuration written with privileges, renaming them would need another privileged step for no user benefit, and the checks keep finding them.

### D13: Build, artifacts and distributions
Everything is built and tested inside one Docker image; the host needs only Docker and make, never Go, Node, Rust or GTK headers. Every `make` target (`check`, `test`, `layers`, `frontend`, `build`, `appimage`, `packages`, `dist`, `test-embed`) runs `docker run` on the image, and CI calls the same targets. **After each milestone** (each task group), `make dist` writes every artifact the milestone has to `dist/` with `SHA256SUMS`, and the group's review task checks them. The image is `build/linux.Dockerfile` from goXterm plus this repository's test tools (`qemu-utils`, `xorriso` for test ISOs, `xvfb`, `swtpm`, `ovmf`) and the `ocvalidate` fetch. `make image check test layers frontend build appimage`; `make test` runs `go test -race` inside the image with `MKG_REQUIRE_TOOLS=1`, which turns today's "skip when the tool is missing" into a failure. Artifacts: `dist/kvm-gui-<v>-linux-amd64`, `dist/kvm-gui-<v>-x86_64.AppImage`, `dist/kvm-gui_<v>_amd64.deb`, `dist/kvm-gui-<v>-1.x86_64.rpm`, `dist/SHA256SUMS`. The packages come from the existing `scripts/package.sh` (`dpkg-deb`, `rpmbuild`), renamed to `kvm-gui`, run inside the image: `.deb` `Depends: libgtk-4-1, libwebkitgtk-6.0-4, qemu-system-x86, qemu-system-gui, qemu-utils, ovmf, pkexec` and `Recommends: swtpm`, with `Replaces`/`Breaks`/`Provides: macos-kvm-gui`; `.rpm` `Requires: gtk4, webkitgtk6.0, qemu-kvm, qemu-img, edk2-ovmf, polkit` (Rocky's QEMU is `/usr/libexec/qemu-kvm`, found per distribution, and lacks some devices such as `vmware-svga`, refused before start by the device check) and `Recommends: swtpm`, with `Obsoletes`/`Provides: macos-kvm-gui`; both ship `/usr/bin/macos-kvm-gui -> kvm-gui`, the desktop entry, the icon and the notices under `/usr/share/doc/kvm-gui/`. The `.tar.gz` is dropped. `LICENSE` and `THIRD_PARTY_NOTICES.md` are embedded in the binary (`kvm-gui licenses`) and copied to `usr/share/doc/kvm-gui/` in the AppImage. Built on Ubuntu 24.04, the glibc floor is 2.39, which Ubuntu 24.04/26.04, Debian 13 (2.41) and Rocky Linux 10 (2.39) meet. Like goXterm's, the AppImage does not bundle GTK/WebKitGTK: each distribution installs its runtime libraries (`libgtk-4-1 libwebkitgtk-6.0-4` on Ubuntu/Debian; `gtk4 webkitgtk6.0` on Rocky 10, where `gtk4` comes from the base repositories and `webkitgtk6.0` only from EPEL: checked 2026-11-08 in a clean `rockylinux/rockylinux:10`, the `.rpm` fails on the base repositories and installs after `dnf install epel-release`, so the docs say to enable EPEL first). Rocky Linux 10 is a fixed target: if its check fails, the release waits. `scripts/check-dist.sh <ubuntu24.04|ubuntu26.04|debian13|rocky10>` installs the documented libraries in a clean container and runs `--self-test` under Xvfb for both artifacts; `scripts/check-gnome.sh` (ported from the archived `reims-gui/scripts`) runs the GUI under Mutter and drives it with agent-desktop.

### D14: Repository moves and CI
- `git mv reims-gui archive/rust/reims-gui` with an `ARCHIVED.md`; nothing outside `archive/` reads it. Its duplicate `crates/rg-reims/reims/` stays inside the frozen archive and is read by nothing (`reims-vgpu` › Reims QEMU packaging folder).
- `reims/` at the root: `Dockerfile`, `Dockerfile.rocky`, `manifest.json`, `package.sh` (from `scripts/reims-package.sh`), `README.md`, and `reims.go` (`package reims`, `//go:embed` of the Dockerfiles and manifest) imported by `internal/core` instead of `internal/core/reims/`. `reims-release.yml` reads `reims/`. Manifest URLs move to `github.com/jniltinho/kvm-gui` (the old URLs redirect, so `reims-c099dd5` keeps working either way).
- **CI on `main` at once:** `reims-gui-ci.yml` and `reims-gui-release.yml` are deleted (Git history keeps them), and a Rust-free `ci.yml` on push and PR replaces the manual `go-ci.yml` in the same commit: `make test` (gofmt, vet, `go test -race`) and `make openspec` (`openspec validate --all --strict`), both inside the image, which carries Node and the OpenSpec CLI from group 1 on. On the feature branch it grows into the Docker-based goXterm form (D13) with frontend `vp check`, `make test-embed` and the clean-distribution checks.
- **Release:** `go-release.yml` requires a green `ci.yml` run on the exact commit (as goXterm's `release-go.yml`), builds in Docker, publishes the AppImage, the binary, the `.deb`, the `.rpm` and `SHA256SUMS` and marks the release latest. A `workflow_dispatch` input `publish: false` builds and uploads workflow artifacts only, for a dry run from any branch. The release publishes all five files.

### D15: The Fyne GUI goes first, on `main`
User decision: Fyne does not need to exist meanwhile. Group 1 deletes the Fyne GUI and `fyne.io/fyne/v2` on `main`, together with the archive of `reims-gui`; until the Wails GUI merges, `main` is the CLI and MCP server only, and `kvm-gui gui` says the desktop GUI comes with the next release. So the Docker image never needs Fyne's OpenGL/X11 packages. `go-release.yml` refuses to publish a commit without `frontend/package.json`, so nothing is released in between; the docs on `main` describe only what `main` has.

### D16: Verification: Codex, agent-desktop, real hardware
- **Codex** reviews every milestone read-only (`codex exec -s read-only -C . "<review prompt>"`); P1/P2 findings are fixed before the milestone is marked done, as AGENTS.md requires.

### D18: GPU passthrough with several VMs
Passthrough stays macOS-only with one reserved GPU at a time (the current single reservation files). With detached runs, Start refuses a second VM set to the GPU while one runs with it, and Release refuses while it is in use, both found through D4's discovery. ### D19: macOS VMs on Reims vGPU through reims-ctl
User decision: do not reinvent what upstream ships. `reims-ctl` (upstream, GPL-2.0-or-later OR LGPL-3.0-or-later) is run as a separate program, never linked, so the BSD-3-Clause app is unaffected; its binary and `reims-util` come in our `reims-<commit>` packages with the corresponding source.
- **Build:** `reims/Dockerfile` pins the newest upstream commit at build time (today `1fe0acb`, after `c099dd5`) and builds QEMU, `reims-ctl` and `reims-util`. A package unpacks entirely into one staged versioned folder `~/.local/share/kvm-gui/reims-ctl/qemu/<build>/` (`bin/qemu-system-x86_64`, `bin/reims-ctl`, `bin/reims-util`, `share/`); `qemu/current` names the active one and `~/.local/share/kvm-gui/bin/{reims-ctl,reims-util}` are links through `current`, so activation switches all three at once after checking all three. The source archive adds `reims-ctl`'s workspace crates and `reims-util` at the revision built, with their vendored crates, and the release task rebuilds offline from it.
- **Environment.** The app runs `reims-ctl` with `REIMS_CTL_CONFIG_DIR=~/.config/kvm-gui/reims-ctl`, `REIMS_CTL_DATA_DIR=~/.local/share/kvm-gui/reims-ctl`, `XDG_CACHE_HOME=~/.cache/kvm-gui` (upstream's own overrides, `paths.rs`) and `REIMS_CTL_QEMU=<the QEMU resolved once by Reims QEMU build's order>` (`install.rs`), so the QEMU the app checks is the one that runs; for a VM added from the user's own `reims-ctl` it uses that VM's recorded configuration folder instead.
- **Create:** the wizard runs `reims-ctl create mac --name <n> --dir <Workspace>/<n> --macos <version> [--offline] --cpus --memory --disk-size --mac`, streaming its output as progress, then `reims-ctl set <n> --ssh-port <free port>`, and registers the VM with `backend = reims-ctl`, its `reims-ctl` name and configuration folder.
- **Run (launch-scoped, never persisted):** the run owner (`kvm-gui vm start`, as for every VM) calls `reims-ctl command <n> -o <run>/reims-cmd.sh` and parses that script with a real POSIX shell parser, `mvdan.cc/sh/v3/syntax` (BSD-3-Clause), without evaluating it. Upstream's `shell_script()` emits `#!/bin/sh`, `# ` comments, `unset NAME`, `export NAME=<word>`, then `exec <program>` with backslash-newline continuations, an option and its value on one line, each word quoted by the `shlex` crate (bare when safe, quoted otherwise, apostrophes escaped). The app accepts only those statement forms with literal words (no parameter expansion, command substitution, globs or redirections) and refuses anything else naming it. Before spawning it does what upstream's `prepare_run` does: create the VM's `logs/` folder, rotate `qemu.log` and (with logs on) `serial.log`, and create upstream's QMP socket folder 0700, refusing one another user owns or others may write into. It refuses parsed options that would detach QEMU or break ownership (`-daemonize`, `-runas`, `-chroot`, any `-vnc`, a second `-pidfile` or one other than the VM's own `<vm>/qemu.pid`-style path upstream emits) and any socket path inside kvm-gui's run folder, without changing the saved settings. Upstream's own `-qmp` socket and `-pidfile` are kept, so `reims-ctl list` (which reads the pidfile and checks QEMU's command line) and `reims-ctl stop` still see the run; the app uses its own `qmp.sock`, `qmp-gui.sock` and `qmp-control.sock`. QEMU's output goes to `~/.local/state/kvm-gui/logs/<vm id>/`. It then starts QEMU itself as its own child (`Pdeathsig`, run record, `qmp.sock`), with the parsed environment plus `SDL_VIDEO_DRIVER=x11` only for an embedded GUI run, and the parsed arguments plus `-vnc unix:<run>/vnc.sock,lock-key-sync=off` and the `qmp-gui`/`qmp-control` monitors in `<run>`. Nothing is written back with `reims-ctl set`, so a later `reims-ctl start` runs exactly upstream's command, and the user's own `extra_args`/`env` are kept as they are (they are part of the parsed command). Shutdown, force stop, pause and the foreground `vm start` behave as for every VM: ACPI over QMP with no automatic escalation, power off only after confirmation. QEMU's image locking refuses a second QEMU if the user also runs `reims-ctl start` on the same VM.
- **Settings:** shown from the parsed command (`-smp`, `-m`, `apple-gfx-pci,...,resolution=`, `displays=`, the `hostfwd` port, the NIC `mac=`), re-read before every start and SSH-port allocation, so external `reims-ctl set` changes are seen; written only with `reims-ctl set` (CPUs, memory, resolution, displays, HiDPI, GPU, audio, SSH port, MAC, stop timeout). Their ports join the port inventory and warnings of every other VM.
- **Installer:** `reims-ctl insert`/`eject` change it for the next start (it is a disk, not a removable drive); the VM window's Devices menu says so.
- **Unsupported for now:** snapshots, clone, export, move and GPU passthrough are refused for these VMs in core, so GUI, CLI and MCP refuse them the same way.
- **Add:** the Manager's Add lists `reims-ctl list --json` entries not registered yet, from kvm-gui's `reims-ctl` folders and from the user's own (`~/.config/reims-ctl`, default variables); the VM row records which configuration folder it belongs to, and every later `reims-ctl` call for it uses that one.
- **Scope:** everything else macOS (VMware SVGA, passthrough, root-patch, versions `reims-ctl` does not support, VMs created before) keeps `internal/core`'s OpenCore, recovery and installer path, which stays in the codebase; its preparation and VARS rules never run on a `reims-ctl` VM.
- **Spike.** Task 2.1 also checks, on the reference host, that the parsed command run by the owner boots a `reims-ctl` VM the same as `reims-ctl start` (window, Metal, SSH forward).
- Alternatives: `reims-ctl` manages every macOS VM (drops Preview and MCP screen for lack of VNC and leaves older macOS behind); `reims-ctl` only for the download (keeps a second OpenCore/disk maker for Reims VMs). Both rejected by the user.

## Risks / Trade-offs

- [Reparenting a foreign X11 window over a GTK 4 WebKit toplevel may misbehave (stacking, input, compositing)] → spike first (task 2.1) with an explicit no-go path that amends the specs before any further work (D6).
- [Frame streaming at 1080p60 through a WebSocket and canvas costs CPU] → dirty rectangles, one frame in flight, coalescing; measured against the Fyne screen (frame time, CPU) before cutover.
- [Rocky Linux 10 may not ship `webkitgtk6.0` in its base repositories] → the clean-container check decides between AppStream and EPEL; Rocky stays a fixed target and the release waits for its check.
- [Detached VMs change behavior users rely on: closing the app used to stop the VM] → the close dialog and the Manager's Shut down make the choice explicit; documented in the release notes.
- [Scope is large (parity matrix)] → milestones in `tasks.md` each end in a Codex review and a verified commit; the matrix makes "done" objective.
- [GPL references could leak into the code] → D2 rule, reviewed by Codex at every milestone (prompt asks to flag copied strings/layouts).
- [Older binaries do not refuse a newer schema] → they never see one: the migration works on a copy in the new data folder (D20) and leaves the old database at schema 5; the release notes say the two apps then have separate VM lists.

## Migration Plan

1. On `main`: delete the Fyne GUI, add the Docker image and Docker-only `make` targets, archive the Rust GUI, disable its CI, create `reims/`, build the newest Reims with `reims-ctl` (release after the user's OK), archive `embed-reims-window-go` and `add-extra-kexts`. No `kvm-gui` release.
2. On `feat/go-wails-gui`: embedding spike, scaffold, core extensions (schema 6, guest types, snapshots, clone), screen stream, embedding spike then implementation, the UI screens, artifacts and checks, each milestone reviewed by Codex.
3. Parity gate: matrix closed, agent-desktop flows green in the GNOME containers, clean-distribution checks green on the four distributions, Nilton VM boots with Reims embedded, screenshots captured.
4. Merge to `main`, tag the next `v*` version, publish the AppImage, the binary, the `.deb`, the `.rpm` and `SHA256SUMS` as latest; keep the last two releases per series.
- **Rollback**: before the merge, `main` is unaffected except for step 1. After release, the previous `macos-kvm-gui` release stays published and still opens its own, untouched `~/.config/macos-kvm-gui/` (D20); VMs created in `kvm-gui` meanwhile are not in it.
