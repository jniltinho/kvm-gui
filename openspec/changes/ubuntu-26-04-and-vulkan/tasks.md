# Tasks

## 1. Venus on the real host (design D5, D6)

- [x] 1.1 Spike on the reference host (Ubuntu 26.04, QEMU 10.2.1): a throwaway VM (the Ubuntu 26.04 cloud image, checked against Canonical's signed `SHA256SUMS`, on a scratchpad overlay with cloud-init; never the Nilton VM's disk) with `virtio-vga-gl,blob=true,venus=true,hostmem=4G` and the memfd backend through `egl-headless` + VNC, on the RX 6700 XT and on the RTX 4070, trying the device selectors; in the guest `vulkaninfo --summary`, `eglinfo -B -p gbm` and `vkcube` (in cage), read back through the VNC socket. Evidence: design D5 "Task 1.1 result". OpenGL is virgl on each GPU, Venus works on both, and `vkcube` renders in the VNC screen (`docs/prints/venus-vkcube-rx6700xt.png`, `venus-vkcube-rtx4070.png`). Mesa's device-select layer breaks Venus when it forces one device, while the loader's `VK_LOADER_VENDOR_ID_FILTER`/`VK_LOADER_DEVICE_ID_FILTER` limits the guest to the chosen GPU, so D5 and the spec now use it (identical GPUs both reach the guest). `/dev/udmabuf` is not needed. QEMU's RSS was 1.49 GiB for a 4 GiB guest, and boot took about 35 s. Moved to 4.1: the run in QEMU's own window (it opens a window on the user's desktop).
- [x] 1.2 Debian 13 and Rocky Linux 10 qualification in clean containers. Evidence: design D6. Debian 13: QEMU 10.0.13 lists `venus`/`blob`/`hostmem`, but there is no render server (`libvirglrenderer1` 1.1.0-2) and the loader (`libvulkan1` 1.4.309) has no device filters, so Vulkan is unavailable for both reasons. Its initialization error cannot be captured in a container (no render node). Rocky Linux 10: `qemu-kvm` 10.1.0 has neither `virtio-vga-gl` nor `virtio-vga`, so 3D is unavailable.
