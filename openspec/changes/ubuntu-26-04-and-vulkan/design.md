# Design

## Context

kvm-gui supports four hosts today: Ubuntu 24.04 (QEMU 8.2.2), Ubuntu 26.04 (QEMU 10.2.1), Debian 13 (QEMU 10.0.13) and Rocky Linux 10 (`qemu-kvm` 10.1.0). The host check asks for QEMU 8.2.2. The reference host is now Kubuntu 26.04 (KDE Plasma on Wayland, kernel 7.0) with an RX 6700 XT (`amdgpu`), an RTX 4070 (NVIDIA 580) and the Ryzen 9 9900X's iGPU, Mesa 26.0 and virglrenderer 1.2.0 with `virgl_render_server`. Its QEMU's `virtio-vga-gl` has `venus`, `blob`, `hostmem` and `max_hostmem`, and `/dev/udmabuf` belongs to group `kvm`. Debian 13's virglrenderer 1.1.0 has Venus compiled in but no render server, which QEMU 10's Venus initialization requests, so Venus is expected to fail there (task 1.2). Rocky Linux 10 ships `qemu-kvm-device-display-virtio-gpu` but no `virtio-gpu-gl`, so it has no 3D at all.

3D acceleration today (commit 08e3786) is the graphics value `virtio-vga-gl`: `guestArgs` adds `-device virtio-vga-gl` with the EDID resolution, and `runArgs` draws with `-display egl-headless,rendernode=<RenderNode()>` behind the VNC socket, or `gtk,gl=on` for QEMU's window. `RenderNode()` takes the first render node with a Mesa driver, and `checkRenderNode` refuses a node the user cannot open. The `gpu` setting and `gpu list` (internal/core/gpu.go) are about passthrough; `GPU` already carries the PCI address, name and driver.

The build image is Ubuntu 24.04 because the binary must run on the oldest glibc among the hosts. Rocky Linux 10 has glibc 2.39, the same as Ubuntu 24.04, so this does not change.

## Goals / Non-Goals

**Goals:**
- Ubuntu 26.04, Debian 13 and Rocky Linux 10 as the supported hosts, with QEMU 10.0 as the minimum, everywhere: checks, Set up host, packages, CI, Reims vGPU and docs.
- Vulkan in Linux and Other guests through Venus, on the host GPU the user picks.
- Clear unavailability where the host cannot do it, before a start rather than at it.

**Non-Goals:**
- Vulkan or 3D for Windows (no Venus or virgl driver on Windows) or macOS (Reims vGPU is its GPU).
- DRM native contexts (`amdgpu`/`i915` native context) and gfxstream: QEMU 10.2's `virtio-vga-gl` does not expose them, and they can come later.
- Moving the build image off Ubuntu 24.04.
- GPU passthrough changes.

## Decisions

**D1. Supported hosts and the QEMU floor.** The minimum system QEMU is 10.0.0: the oldest of the three hosts (Debian 13) and the first with the Venus support kvm-gui relies on. `checkQEMUVersion` fails below 10.0 with the hint naming the supported hosts. A new `Supported host` check reads `os-release` (`ID`, `VERSION_ID`, `ID_LIKE`): Ubuntu ≥ 26.04, Debian ≥ 13 and Rocky ≥ 10 are OK, anything else is a Warning, not a Failure, so a capable unlisted host still works. Set up host keeps its package tables for the three hosts and refuses Ubuntu releases older than 26.04 (it would install a QEMU that fails the check). Reims VMs run Reims's own QEMU, so the floor applies to the system QEMU only.

*Alternative:* keep 24.04 with 3D/Vulkan disabled there. Rejected, because the user chose to drop it, and its QEMU 8.2 has no Venus.

**D2. Packaging, CI and checks without 24.04.** `ci.yml`'s distribution matrix and `check-dist.sh` drop `ubuntu24.04`. The `macos-kvm-gui` 0.13.0 upgrade check moves to `ubuntu26.04` (with `rocky10`), after checking that the 0.13.0 `.deb` installs there. `check-gnome.sh` runs the X11 embedding check on Debian 13 (GNOME 48 still has an X11 session) instead of Ubuntu 24.04, and keeps Ubuntu 26.04 as the Wayland-only check. Reims vGPU: `reims-release.yml` and `reims-upstream.yml` build `ubuntu26.04`, `debian13` and `rocky10`, and the corresponding-source archive, today made only in the `24.04` job, moves to the `26.04` job (the workflow then checks that the archive and its checksum exist). The Docker build stays what the code does today, Ubuntu only, now `26.04` only: Debian 13 and Rocky Linux 10 hosts install the prebuilt package, and the `reims-vgpu` spec is narrowed to say so. `reims/Dockerfile` defaults to 26.04 and `reims/manifest.json` loses its `ubuntu24.04` entry. v0.15.0 and the Reims release it pins (`reims-1fe0acb`, which has the 24.04 package) become retention exceptions in `AGENTS.md` and the release skill, so the two-per-series rule never deletes what 24.04 users need. The build image keeps its Ubuntu 24.04 base and is documented as a build ABI, not a supported host.

**D3. Vulkan settings.** `Config` gets `vulkan` (bool) and `render_gpu` (a PCI address such as `0000:03:00.0`, empty for automatic). Validation: `vulkan` needs graphics `virtio-vga-gl`, and saving graphics other than `virtio-vga-gl` clears `vulkan` (the GUI does it visibly; the CLI and MCP refuse `vulkan=true` without 3D, as the spec says); `render_gpu` is empty or a well-formed PCI address, and its presence is checked at start, not at save (a GPU can come back). Neither applies to macOS or Windows VMs. The new `config set` keys are `vulkan` and `render-gpu` (`auto` clears it), also in `AgentConfigKeys` for `vm_config_set`. The name avoids the passthrough `gpu` key.

**D4. Host GPUs for 3D.** `RenderGPUs()` lists `/sys/class/drm/renderD*` with each node's PCI address (`device` link), vendor:device, driver and name (the names `gpu list` already uses). GPUs bound to `vfio-pci` have no render node, so they never appear. `RenderNode(c)` resolves `render_gpu` to the node at start time, or applies today's automatic rule when it is empty. The start refuses a named GPU that is missing, naming it and Settings › Display, and refuses a node the user cannot open for reading and writing, for both display modes. The choice applies where QEMU can direct it: in the app's screen, `egl-headless,rendernode=` draws OpenGL on it. QEMU's own window (`gtk,gl=on`) has no render-node option and always draws OpenGL on the desktop's GPU, so with `display=window` the Host GPU setting applies to Vulkan only, and Settings says so. The GUI catalog carries the list and the automatic pick, so Settings can say "Automatic (AMD Radeon RX 6700 XT)". `gpu list` adds a "3D" column (render node or "—").

**D5. Venus command line.** With `vulkan`, the device becomes `virtio-vga-gl,blob=true,venus=true,hostmem=<H>` plus the EDID options. Guest RAM moves to a shared memfd backend, `-object memory-backend-memfd,id=ram0,size=<RAM>M,share=on` and `-machine q35,memory-backend=ram0,...`, because blob resources map guest memory into the host renderer. `-m` stays as is. `H` is 4 GiB, a host-visible window that is not allocated up front; Venus on discrete GPUs works with it, and there is no setting for it (a non-goal unless a guest needs more). The display stays `egl-headless,rendernode=<node>` behind VNC, or `gtk,gl=on`, *if task 1.1 confirms blob scanouts work there on QEMU 10.2*. If not, the design picks the display that does and records it here before any code. To limit the guest to the chosen GPU's Vulkan device by its PCI address, not by vendor:device (two identical GPUs share that), the QEMU process gets `DRI_PRIME=pci-<domain>_<bus>_<dev>_<fn>` and `MESA_VK_DEVICE_SELECT_FORCE_DEFAULT_DEVICE=1`. Mesa's device-select layer reads both, and it is implicit for every ICD, NVIDIA's included. The environment is the parent's with only these variables replaced, set per QEMU process, never in kvm-gui's own environment. Variables that would bypass or override the layer are removed from the child's environment: `MESA_VK_DEVICE_SELECT`, `VK_LOADER_LAYERS_DISABLE`, `VK_LOADER_LAYERS_ENABLE`, `VK_INSTANCE_LAYERS`, `VK_LOADER_DEVICE_SELECT` and `VK_LOADER_DRIVERS_SELECT`/`_DISABLE`, and `VK_ICD_FILENAMES`/`VK_DRIVER_FILES`. Before such a start, kvm-gui checks that the device-select layer's manifest is installed (`VkLayer_MESA_device_select.json` under `/usr/share/vulkan/implicit_layer.d` or `/etc/vulkan/implicit_layer.d`) and is not disabled by its own `disable_environment` key, and refuses a Vulkan start with an explicit Host GPU when it is missing, naming the package (`mesa-vulkan-drivers` on Ubuntu, Debian and Rocky Linux). Task 1.1 checks that the guest then sees exactly the chosen GPU, on both GPUs. If it does not (layer missing or ignored by virglrenderer's renderer), an explicit Host GPU is refused for Vulkan VMs, which keep the automatic choice, and the spec is amended before code.

**D6. Capability probes.** A cached probe asks the host's QEMU `-device virtio-vga-gl,help`. No device means 3D is unavailable. Vulkan is available on the host only when the `venus` property is present and virglrenderer's render server is installed (`virgl_render_server` in `/usr/libexec` or `/usr/lib/virglrenderer`, which QEMU 10 requests with Venus). It is available *for a GPU* only when a Vulkan ICD for that GPU's kernel driver is installed (`amdgpu`/`radeon` → RADV, `i915`/`xe` → ANV, `nouveau` → NVK, `nvidia` → NVIDIA's ICD, read from `/usr/share/vulkan/icd.d` and `/etc/vulkan/icd.d`), so the Host GPU list marks GPUs without one as "no Vulkan driver". `/dev/udmabuf` is a condition only if task 1.1 shows the in-app scanout path needs it (QEMU exempts virgl blob configurations from its own udmabuf check). Each failed condition is its own reason string. This qualification is static: the availability contract is "the host has what Venus needs", not "Venus will initialize". A start where virglrenderer still fails shows QEMU's error in the VM's log and the start message, as the spec requires. The GUI catalog exposes `can3D`, `canVulkan` and their reasons, and the start checks reuse the same probe, extending today's "Devices the host's QEMU lacks" check. Venus also needs `/dev/udmabuf` readable and writable for blob scanouts, so the start refuses with a hint when it is not (`kvm-gui setup` adds the user to group `kvm`, which owns it on Ubuntu 26.04; tested in 1.1 whether it is needed with `hostmem` at all).

**D7. Surfaces.** Settings › Display, under 3D acceleration, adds a "Vulkan (Venus)" checkbox and a "Host GPU" dropdown (Automatic first, then each GPU with name and driver), disabled with their reason when the probe says so. The New VM wizard keeps only its 3D checkbox: Vulkan and the GPU are Settings options. The CLI and MCP use D3's keys, and `vm status` / `vm_status` mention Vulkan and the GPU in use.

## Risks / Trade-offs

- [Venus with `blob=true` may not scan out through `egl-headless`] → task 1.1 tries it first on the real host. If it fails, Vulkan is not offered for the in-app screen. The spec's in-app scenario and task 4.1 are amended together with D5 before any code, and no silent fallback is allowed.
- [NVIDIA's proprietary driver with virglrenderer] → task 1.1 runs OpenGL and Vulkan on the RTX 4070. Venus in QEMU still needs virgl's EGL context on the chosen node, so if EGL/virgl fails there, NVIDIA GPUs are not offered for 3D at all (with the reason), recorded in D4 and the spec's NVIDIA scenario amended.
- [A shared memfd backend changes how guest RAM is allocated (no THP by default)] → applied only to Vulkan VMs; measured once in 1.1 (boot time, RSS).
- [Ubuntu 24.04 users upgrading] → the release notes and README say v0.15.0 is the last for 24.04. The host check warns, and the QEMU check fails, with the reason, so nothing breaks silently.
- [Guests whose Mesa lacks the virtio Vulkan driver] → Settings' help text and `docs/guests.md` name the guest's requirement (Mesa with `virtio` Vulkan, for example Ubuntu 24.04 or later). The guest falls back to llvmpipe/lavapipe, nothing fails.

## Migration Plan

Additive for settings: the new `vulkan` and `render_gpu` fields default to off and automatic, and no stored data changes. Dropping 24.04 is a release-level break: v0.16.0's notes say so, and 24.04 users keep v0.15.0. This change is archived after `migrate-gui-to-go-wails`, whose `desktop-app`, `reims-vgpu` and `host-preflight` deltas it modifies.

## Open Questions

- Whether `DRI_PRIME=pci-…` with `MESA_VK_DEVICE_SELECT_FORCE_DEFAULT_DEVICE` reaches virglrenderer's Venus renderer (resolved by 1.1).
- Whether NVIDIA's driver is usable for virgl OpenGL and Venus on this host (resolved by 1.1).
